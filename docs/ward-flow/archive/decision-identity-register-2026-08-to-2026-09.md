# Ward Flow decision identity register, August to September 2026

> Archived 16 October 2026. This was section G of [the decision ledger](../../ward-flow-ledger.md). It is history: new decisions take a D number in [the decision log](../decisions.md). Kept so older `WB-`, `FD-`, `TR-` and similar ids can still be looked up.

## G. Identity register

**One session assigns every decision number (rule 9), and this is where it does it.** A number exists
from the moment it is assigned; its reasoning is written by whoever owns the relevant specification.
This section makes the gap between the two visible, because an assigned-but-unwritten decision is
exactly the thing that otherwise rots quietly.

### Series, and the boundary between them

| Series                               | For                                                     | Home                       |
| ------------------------------------ | ------------------------------------------------------- | -------------------------- |
| `WB-`, `WB-DB-`, `P3-`…`P8-`, `MET-` | **What the system does.** Product decisions             | The relevant specification |
| `PROC-`                              | **How the work is done.** Process, review, verification | The process documents      |

**Product namespaces are per-document; a new document gets a new one.** `FD-` (referral front door) was opened 2026-08-29 for `docs/superpowers/plans/2026-08-29-ward-flow-referral-front-door.md`. **`RF-` was proposed and rejected: `RF-001` is already a synthetic REFERRAL RECORD id in the data model** — a decision `RF-1` beside a record `RF-001`, in the same documents, about the same subject, is the collision rule 2 exists to prevent. **Check a proposed prefix against data as well as against decisions — and check it against data that could plausibly exist, not only data that does.** `RF-` was caught because `RF-001` is real today. A prefix like `MH-` or `ED-` would pass a search against the current fixtures and still read as a record id the moment somebody adds one — **the collision then arrives from the data side, later, and nobody re-runs a prefix check when a fixture grows.** So the durable form is not "is this prefix unused" but **"could this prefix ever plausibly be a record namespace"** — prefer one that could not. `FD-` passes both. _(Extension contributed by the settings/process session.)_ **CORRECTED 2026-08-29 — this rule used to say "these two families are the whole set, no third may be opened". That is a COUNT, and counts are brittle.** The principle is not _two_; it is that **a series is opened deliberately, with a stated boundary, and only when no existing series fits.** Two is a description of today. Were a genuinely different kind of decision to arise, the old wording would either be broken or abandoned, with no third option — which is how the five-facts rule failed. The test before opening any
series at all is rule 9's: check whether the project already has one. `PROC-` was opened deliberately
on 2026-08-29 rather than by accident, which is the distinction that matters.

### DECIDED is not IMPLEMENTED, and this ledger did not distinguish them

**Every decision row now carries one of two states.** `DECIDED` means the owner ruled and it is
written down. `IMPLEMENTED` means code changed. **This ledger conflated them until 2026-08-29 and
was wrong about at least one decision as a result.**

**The case that forced it — `WB-DB-11`, dropping the morning page's frozen view.** Commit
`e43f3f8f8`, message _"Ward board: the frozen morning view is dropped, everything is live (DB-11)"_.
`git show --stat`: **37 insertions, one design document, no code.** On the live branch the morning
page still holds `useState<FrozenMorning>` and `useState<MorningView>("fixed")` — **the freeze is
present and is still the DEFAULT view.** Verified here, not relayed.

**The transferable rule: a commit that RECORDS a decision has the same message shape as one that
IMPLEMENTS it.** `e43f3f8f8` is entirely truthful about its own subject — the decision _was_ made,
and the message describes it accurately. **`git log` proves a decision exists; only `git show --stat`
or the file itself proves anything shipped.** Found by the settings session auditing its own plan
against the code, which had recorded the freeze as already gone on the strength of that message.

**Its three siblings are UNVERIFIED, and my check was too weak to settle them.** `WB-DB-7`,
`WB-DB-10` and `WB-DB-12` were all decided "at the fold". Grepping for guessed symbol names returned
"no sign" for two — **which is exactly the narrower-than-the-question failure rule 11 names, so I am
recording it as unverified rather than as a finding.** Someone should check them properly, by reading
the morning page rather than searching it for names I invented.

### Every row is one of two types, and they need OPPOSITE maintenance

**A document states either a fact about NOW or a record of what was true THEN.** Correct the first.
**Date the second and never back-date it** — back-dating destroys the provenance that caught a
handover instructing a reader to undo a decision the owner had made nine hours earlier.

**This supersedes and explains the conditional convention below, which was the special case.** A
conditional row is not a _weaker_ record; it is a **correctly-typed** one. **A row asserting a
measurement without its date is a TYPE ERROR, not merely a risk** — and that is a stronger statement,
because a discipline ("remember to mark this one") fails quietly while a malformed row can be
recognised on sight. _(Framing contributed by the settings/process session, which is right that it
subsumes the convention.)_

### Decisions conditional on a measurement

Some decisions are correct _because of a number_, and the number moves. Marking them
`CONDITIONAL` puts the measurement, its timestamp and the command to re-take it in the row, so a
reader in three weeks sees that the basis has aged rather than reading a stale measurement as a
standing fact. **A decision that quietly stops being true is worse than one that was wrong from the
start — the wrong one gets argued with.** _(Convention proposed by the settings/process session.)_

**`PROC-3` — converge to one line.** Justified as "nearly free today". Measured by the settings
session, then **re-taken by this session hours later and already moved**:

|                           | Their reading | Re-taken 2026-08-29 21:57 |
| ------------------------- | ------------- | ------------------------- |
| `print-fixes` ahead       | 4             | **5**                     |
| behind the main line      | 5             | **8**                     |
| **changed on BOTH sides** | **0**         | **0**                     |
| merge                     | clean         | **clean**                 |

**Only the third row is load-bearing.** Ahead and behind drift with every commit and cost nothing;
**zero files changed on both sides is what makes the merge free**, and the moment it is non-zero the
decision's justification is gone. Re-take before acting:

```bash
A=claude/ward-flow-print-fixes; B=claude/ward-flow-phases-6-7-design; M=$(git merge-base $A $B)
comm -12 <(git diff --name-only $M $A|sort) <(git diff --name-only $M $B|sort) | wc -l   # want 0
```

**The convention needed one more field, and PROC-3 is how we found out: record WHAT WAS MEASURED, not
only what the numbers were.** The re-take command above names `claude/ward-flow-print-fixes`. That
happens to be right — but this session reached that name by inheriting it from another session's
report, not by asking a worktree, and the ownership registry said something different. **A re-take
command that names a branch inherits every assumption in that name**, so running it tomorrow could
return a perfectly healthy number about the wrong branch, and the row would read as valid
indefinitely. The convention now requires the _subject_ to be re-verified, not just the number:

```bash
git -C <worktree> rev-parse --abbrev-ref HEAD    # ask the worktree, do not infer the branch
```

**And the sharpest form of it, which generalises past this project.** Every session held a warning
saying _"of the three `ward-board*` branches, only the unsuffixed one carries work"_. The live branch
was in none of that family — it is `claude/ward-flow-print-fixes`, named for a task that grew into
the board work and was never renamed. **A check phrased as "which of these is right?" cannot return
"none of them."** A question with a false premise returns a confident wrong answer and no error, and
every session that consulted that warning got one. The replacement is the only check that cannot be
wrong about itself: ask the worktree what branch it is on. _(Found by the fold session.)_

This is the same family as the prefix rule: **a justification that expires through ordinary correct
work**, with nobody at fault and no signal at the moment it stops holding.
