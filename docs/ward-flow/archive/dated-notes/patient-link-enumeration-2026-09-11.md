# The patient-link enumeration (D-14, task `ward/task-patient-link-guard-20260911`)

**What this is.** D-14 forbids me from deciding which screens or derivations may read
`Referral.patientId` / `Admission.patientId`. This file is the enumeration the ruling asks for
instead: every place that could legitimately want to read the link, what it would use it for, and
whether it is "a ward seeing its own patient" or "a ward seeing somebody else's history." **Nothing
below has been opened.** The default-deny guard (`tests/ward-patient-link-default-deny.test.ts`)
refuses every one of these that is not already reading the link today, and the two that already do
are recorded, not newly permitted.

Read `docs/ward-flow/owner-decisions-2026-09-1x.md` §D-14 before ruling on any of this.

## 🔴 The one that needs a ruling now, not later

**`src/components/ward-management/search/record-preview.tsx`** and
**`src/components/ward-management/search/patient-typeahead.tsx`** already read
`Referral.patientId` — shipped 2026-09-05, before this task existed. Both are scoped deliberately
(their own header comments say so): one referral, its own state, never a history across several.
Until this task, that read was **inert on the shipped fixture** — every seeded `Referral.patientId`
was unset, so the code path existed but could never resolve to anybody. **This task's own seed
population (`RF-010` → `PT-001`, `RF-RPHS-14` → `PT-003`) is what makes it resolve for the first
time.** Nothing about those two files changed; what changed is that the data can now reach them.

- **What it shows:** from the search console, typing a patient's name and selecting them shows
  their own linked referral and (through it) the open movement it led to, in one preview panel.
- **Classification:** a ward/coordinator search screen seeing **its own searched-for patient's own
  single referral** — not a history, not another ward's referral, not "where else has this patient
  been." Both files' own comments argue this explicitly and cite FD-23 by name.
- **Why it needs the ruling anyway:** the reasoning is an implementer's, not an owner's or Ward
  Lead's. Nobody has confirmed that "one referral's own tie, shown from a network-wide search
  console" is the intended shape now that it is live rather than theoretical. D-14 says this
  ruling's failure direction is not symmetric — this is the first moment that asymmetry is real.
- **Action needed:** Ward Lead confirms this is the intended, permitted shape (in which case it
  should be added to the default-deny guard's allowlist with that ruling cited), or narrows/removes
  it.

## What I did not do

I did not wire the gender/sex-mix gate to `Patient.gender` via `Admission.patientId`. That
derivation is exactly the "which screens/derivations may use the link" decision D-14 reserves for
Ward Lead. The join now EXISTS and is real (not manufactured — see `Admission.patientId`'s own doc
comment for the derivation, and the two genuine referral↔admission↔patient chains this task's seed
adds), so that gate is now buildable in a follow-up task, but it is not built here.

I did not add `patientId` to any of the "candidates" table above, and I did not remove or alter the
two pre-existing readers. Both are exactly as this task found them, except that they can now
sometimes resolve to a real person where before they never could.
