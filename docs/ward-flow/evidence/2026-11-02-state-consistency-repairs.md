### Schema and rollout boundary

Migration `017-forecast-consistency.sql` and its rollback are prepared and checksum-registered, but **neither has been applied**. Shared history is readable on schema 16; the new backend explicitly refuses shared writes until schema 17. A writable response requires the versioned contract, so the browser cannot mistake a local fallback for a confirmed shared save.

Before any separately authorised rollout, stop all older schema-16 last-writer-wins backend writers. A new backend can run read-only forecast history on 16 while the upgrade is prepared. Apply 017 through the existing administrator migration workflow, then use the new versioned clients. Do not leave an old writer running against the upgraded table: old code would not advance the new per-day version. Refresh old clients rather than treating their legacy POST format as safe.

The migration takes the workspace lock, advances workspace revisions and backfills reason versions from those new revisions. Rollback preserves values and receipts; reapplying advances revisions again, preventing stale pre-rollback versions becoming current again. No database credentials, settings, provider calls or hosted writes were used here.

`historyRevision` orders persisted history atomically; it is not a claim that a browser's first daily forecast calculation used that board revision. The existing first-view-per-day capture semantics are preserved. Real PostgreSQL locking, upgrade/rollback execution and deployed acceptance remain separate unrun checks.
