# Silent data loss paths, 10 November 2026

Audit M8 from the master audit list: every way work in a Ward Flow tab can vanish, and the test that shows it is saved or warned about. Audience: whoever changes saving, sign-out, drafts or Undo. Status: point-in-time record at `3f4b9571b` plus branch `audit-b-data-loss`. Evidence boundary: the named tests ran locally in jsdom or Node; real browser unload behaviour (when `beforeunload` and `pagehide` fire, and what the browser's own warning says) was not observed.

By design (D-18, D-72 item 2), typed text and board data are not kept on the device, with one narrow exception: D-67 lets the opted-in synthetic referral drawer and legal form editor keep a session draft in `sessionStorage` for refresh recovery. Waiting saves live in memory only (`SharedWorkspaceClient`, `offlineHold`, `queue` in `ward-shared-client.ts`). Receipt recovery (`recordCommandRecovery`, `recoverReceipt`) keeps opaque identity metadata only: each command ID with its receipt scope, expiry and phase (queued or sent), never a command body or typed content (`ward-command-recovery.ts`). So a lost tab loses its unsent work, and the protection is a warning before it goes.

## Gaps left for Josh

- **A. Session limit.** Closed by D-125 (Josh, 10 Nov 2026). Forced expiry still never waits, but the sign-in screen now says that changes still waiting were not saved (`UNSENT_CHANGES_DROPPED_NOTICE`). It gives no count and names no record.
- **B. Sign out or Switch role inside an Undo window.** Closed by D-125. Sign-out and role switch send held actions first (`ward-held-actions.ts`) and wait for them in `use-ward-supabase-shared.ts`; a refused or failed save keeps the session.
- **C. A hidden tab.** The Undo window keeps running in a hidden tab (`wf/toast.tsx`), so it normally ends and records there. A phone that freezes or discards the tab first, without `pagehide`, still loses the batch. Recording on `visibilitychange` would end Undo on every tab switch, so it was not done.
