## 2. What this drawing is for, and the difference from each surface

The drawing's own header comment (`referrals-third-edition.html:4660-4670`) states its purpose: **"the triage list, oldest first, and the decision on each,"** holding only a `Referral` dataset, explicitly **"NOT Command's queue re-skinned."** That sentence differentiates it from the _bed-placement_ priority queue (movements awaiting a ward bed, a different screen entirely) — it does **not** mention surface A/B at all.

- **vs A (Referral board):** 🔴 **I cannot state a real difference.** The drawing's Triage list is sorted by the same two keys (urgency tier, then wait) as `referralQueueOrder`, carries the same "New referral" affordance, and its Decision panel accepts/declines with the same fixed reason vocabulary. Functionally this reads as a visual redesign of A, not a screen answering a different question for a different user.
- **vs B (Match view):** Real difference, but it cuts against the drawing rather than for it — see §5. The drawing's "Accept to the pathway" has no unit, no candidate list, no travel bands, no override path; the real acceptance act (B) is entirely about _which_ unit. The drawing's own comment (line 4676-4678) calls single-destination-per-referral "a simplification… reported in the build report," so this is a known, named gap rather than a hidden one — but it means the drawing cannot currently answer the question B answers.
- **vs C (Intake):** Clear difference. The drawing's "New referral" menu explicitly says "Opens the Raise a referral screen with the source prefilled. Not wired in this prototype" (line 4626) — it defers to C rather than duplicating it.
- **vs D/E (embedded ED/community inboxes):** Clear difference by scope: D and E are single-department/single-team views; the drawing is network-wide across all four health services, matching A's scope, not D/E's.
- **vs F:** No overlap; F carries no referral list at all.

**Bottom line, stated plainly because the brief requires it:** the one surface this drawing cannot be told apart from on the evidence read is **A, the existing Referral board** — the exact confusion Josh named. If this drawing is to become a real, buildable screen, it needs either (a) a stated reason it is a _different_ screen from A (different role, different question, different act — none of which I found in the file), or (b) to be understood as a proposed **redesign of A itself**, not an additional screen. That is a decision for the owner, not something this reading can settle.

## 3. The drawing's sections, in order

1. **Header bar** — title "Referrals", synthetic-prototype badge, universal search (scoped to referral IDs only), service-scope menu (all/one of the four health services), Activity/Tasks/Tools drawers, "New referral" menu (ED or community-team source, not wired), "Triage" primary button (selects+scrolls to the oldest undecided referral).
2. **Triage list** panel — the queue of referrals not yet decided, oldest-most-urgent first.
3. **Referral detail** panel — the facts of the selected referral (source, destination, two clocks).
4. **Decision and reasons** panel — Accept to the pathway / Redirect (not wired) / Decline with a reason (fixed 7-item grid), or, once decided, a one-line record of what happened.
5. **Rail** — navigation to the other Ward Flow sections, plus a foot carrying the invented-data disclaimer and the page's own reconciliation check (tier counts sum to total).

## 4. Per-section data and its producer, or NOT IN THE MODEL

- **Triage list:** needs `Referral[]` filtered to undecided and ordered by `(urgency, raisedAt)` — real producer `referralQueueOrder` (`ward-referrals.ts`). Tier wording should be `urgencyTierLabel` (`ward-priority.ts`); the drawing hand-rolls its own `tierLabel()` (line 4879) rather than importing it — exactly the "two spellings of one field" defect class `referral-board.tsx:33-38` already paid for once.
- **Referral detail:** `source` (`REFERRAL_SOURCES`, `ward-model.ts:1243`), `ageBand`, `homeService`/`homeRegion`, `destination` (`ReferralDestination` union, `ward-model.ts:1375`), and the two clocks via `referralClocks`/`REFERRAL_CLOCK_TERMS` (`ward-referrals.ts`). All present in the model.
- **Decision — Accept:** 🔴 **NOT IN THE MODEL as drawn.** The real `ACCEPT_REFERRAL` event requires a `unitId` for a ward destination (`referral-match.tsx:243-255`); the drawing's "Accept to the pathway" names no unit at all. It cannot be wired to the real reducer without adding the candidate list this screen deliberately omits.
- **Decision — Decline:** producer exists — `REFERRAL_DECLINE_REASONS`/`DECLINE_REASON_LABELS` (`ward-model.ts:1294`, `ward-referrals.ts:881`) — but see §6 for why applying this one list to every destination kind is already stale.
- **Decision — Redirect:** 🔴 **NOT IN THE MODEL.** No reducer event moves a referral from one destination kind to another; the menu says so itself ("Not wired in this prototype," line 4626/5163).
- **Rail reconciliation check:** derived in-page (`reconcile()`), not read from any model file — fine as a page-local consistency check, not a clinical fact.

## 5. What cannot be built honestly

- **Accept, as drawn.** A ward acceptance without naming a unit is not the act the real model records (§4). Building the drawing's simple accept button as-is would create a second, easier-looking "accept" that does not match `ACCEPT_REFERRAL`'s actual contract.
- **One decline-reason list for every destination.** Per owner ruling **O-16.6** (`docs/ward-flow/archive/dated-notes/owner-decisions-2026-09-1x.md:2252`), a community team's decline reasons are a _separate, five-item list_, never the seven ward reasons stretched to fit — "not one of the seven fits." The drawing applies the ward's seven-item grid uniformly, including to the two community-destined referrals in its own fixture (RF-007, RF-004). This is not yet wrong in the _shipped_ code (the five-item community list does not exist there either), but it is a ruling this drawing predates and would need to honour before being built.
- **Redirect.** No model event exists for it. Naming what it would need: a reducer action that moves (or adds) a `ReferralAddressing` of a different `kind` for an existing referral, plus a decision on whether the old addressing is cancelled, withdrawn, or left live alongside the new one (the model already supports _parallel_ addressings, FD-24, so "redirect" may really mean "add another addressing" rather than "replace one" — that is a real design question, not named in the drawing). Not designed here, per instruction.
- **⚠️ Referral withdrawal.** Flagged gap, confirmed live: **FD-5** (`owner-decisions-2026-09-1x.md:2169`) — "no withdrawal event exists, so a referral abandoned by the referrer stays `queued` forever." The Triage list this drawing renders inherits that exact gap: a referral the referrer has abandoned will sit at the top of this screen's queue indefinitely, exactly as it does on the real board today. This screen does not make the gap worse, but it does not fix it either, and a coordinator using it would have no way to tell "still live" from "abandoned but stuck." Naming what it would need: a `WITHDRAW_REFERRAL` event, a new `ReferralState`/addressing state, and a place on this screen to both action and display it — not designed here; per **O-16.1** any such growth goes to the owner individually, named, never assumed.
- **Community team closing a case.** Not directly rendered by this drawing's three sections (it has no community-team caseload view), so it does not need this screen to solve it — noted only because the brief asked it be checked against every section, and none of the three needs it.

## 6. Owner decisions that bind this screen

- **FD-23** (`ward-referral-visibility.ts:22-49`, owner ruling 2026-08-30): a ward may not see where else a patient has been referred; only the coordinator sees everything. This screen's Referral detail/Decision panels show the full referral including its one destination and would need to show _every_ addressing if built to parity with B — so it must be built and gated as **coordinator-scoped only**, never reachable from a ward role. Nothing in the drawing states this scoping; it should be recorded before build.
- **O-16.6** (five community decline reasons, own list) — see §5. Binding: do not let this screen's decline grid apply the ward's seven reasons to a community-destined referral once built.
- **FD-5 / O-16.1** (no withdrawal event; "the app grows but you notify me what needs to grow," `owner-decisions-2026-09-1x.md:2153-2187`) — binding: do not add a withdraw control to this screen without individual, named owner approval.
- **D-18/D-19** (referral _source_ vs referral _route_ naming collision, and cross-referral visibility scoping, `owner-decisions-2026-09-1x.md:880-939`) — the drawing's `SOURCE_LABELS` correctly uses the six real `REFERRAL_SOURCES` values (`community`, `crisis_service`, `police`, `ambulance`, `inter_hospital`, `ed_medical`), not the broken three-value facade type D-18 flagged — this is a point of compliance, worth preserving rather than "fixing" back to the wrong shape.
- **The decline-reason-must-not-default rule** (`referral-match.tsx:154-167`): the real screen learned, the hard way, that a decline control must start unchosen and refuse to submit until a reason is picked. The drawing already does this correctly (`aria-disabled` until `state.declineChoice` is set) — confirm this is preserved if rebuilt in React, not silently dropped for a simpler default-selected control.

## 7. Catchers

- **Triage list:** a test asserting the rendered order equals `referralQueueOrder(referrals)`'s order exactly, on a fixture with mixed tiers and wait times (catches a reversion to a single sort key).
- **Referral detail:** a test per destination kind (ward/ED/community) asserting the fields shown match `Referral`'s own destination union — catches a ward-only field (e.g. `sex`) leaking onto a community-destination row.
- **Decision — Accept:** once a unit is added to close the §5 gap, a test that `ACCEPT_REFERRAL` cannot be dispatched without a `unitId` for a ward destination (mirrors `tests/ward-referral-reducer.test.ts`'s existing shape).
- **Decision — Decline:** a test that a community-destined referral's decline control offers only the community list, never the ward's seven — the direct catcher for the O-16.6 gap named in §5/§6.
- **Rail reconciliation:** the existing in-page `reconcile()` check, kept red-on-mismatch exactly as built.

**🔴 The extra catcher — protecting the owner's "these are two separate screens" instruction:** a test that fails if this screen and the existing Referral board (surface A) are ever folded into one. Concretely: assert both routes exist (`/mockups/ward-flow/referrals` rendering `ReferralBoard`, and whatever route this drawing becomes) with **distinct root `data-testid`s**, and assert `ward-nav.ts`'s nav list still carries two separate entries for them. Such a test fails the moment somebody — reasonably, having read this drawing's own "not Command's queue" comment and missed that it never distinguishes itself from A — deletes one component as a "duplicate" of the other. Given §2's finding, this catcher is not a formality here; it is the one thing standing between this drawing and exactly the merge Josh asked to be prevented.

## Limits of this reading

- I did not run the app, so I have not confirmed at runtime that `ReferralBoard`/`ReferralMatchView` render exactly as their source reads, or that `community-home.tsx`'s referral list behaves as its surrounding comments describe — this is a static read only, as instructed.
- I read `docs/ward-flow/archive/dated-notes/owner-decisions-2026-09-1x.md` by targeted search (decline reasons, referral sources, withdrawal, privacy scoping, plus the sections those hits sat in) rather than end to end; the file is large and there may be other rulings bearing on this screen I did not surface.
- I did not find a literal "REFERRALS" tally on a real Command/hub screen matching the drawing's comment "matching Command's REFERRALS" (line 4674) — that phrase may refer to a sibling third-edition drawing rather than the shipped app; I have not confirmed which.
- Section §2's "cannot differentiate" finding is the single most consequential claim in this contract and rests on reading both files' stated purposes and behaviour, not on an owner statement that they are meant to be the same or different screen. It is reported as a finding for the owner to rule on, not a conclusion.

If a decision arises here that this brief does not cover, it has been stopped short of and handed back rather than decided.
