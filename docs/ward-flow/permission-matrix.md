> any layer disagreement not listed below. Audit 7, issue #1570.

Who may take each action, by desk, in the shared (signed-in) workspace with synthetic data. `Y` means every
layer that decides lets the desk take the action; `-` means every such layer refuses it; `!` marks a known
disagreement listed under [Known disagreements](#known-disagreements). A `Y` is about the role only: the backend
and the reducer still limit each desk to records in its own place.

| Screen   | `dispatchPermission` (`ward-role-permissions.ts`) for the shell role (`chromeRoleForAccess`); demo controls from the server's `demoControls` flag; no role shows the ask-for-access gate | Called per cell                                     |
| Engine   | `EVENT_ROLE` (`ward-flow-event-roles.ts`) as enforced by `wardFlowReducer`                                                                                                               | Reducer run on the synthetic seed with a bare event |
| Backend  | `deskCommand`, the role clause of `validSharedCommand` and `commandRefusal` (`backend/ward-flow/engine.ts`); no role is refused 403 in `shared-http.mjs`                                 | Called per cell                                     |
| Database | Row level security policies and grants in `backend/ward-flow/migrations/` and `infra/`                                                                                                   | SQL read as text                                    |

## Database

Every one of the 17 `ward_flow` tables has row level security with the `runtime_only` policy (the `wardflow_backend` role alone), and no grant names a browser role. No app role reaches a row except through the backend, so the database defers every cell to the backend column.

Membership roles the database accepts: `admin`, `bed_manager`, `community`, `coordinator`, `ed`, `executive`, `officer`, `ward`.

## Known disagreements

None. Every deciding layer gives the same answer for every action and desk.

## Not covered

- **Engine, 84 cells read statically.** For these actions and desks the reducer throws on a bare event (it reads the payload before it answers), so the engine cell falls back to `EVENT_ROLE`, the table the reducer's role gate reads: `ACKNOWLEDGE_INBOX_ITEM` (coordinator, coordinator_service, officer, ward, bed_manager, ed, community, executive, admin), `COMPLETE_BED_MEETING_ACTION` (coordinator, coordinator_service, officer, ward, bed_manager, ed, community, executive, admin), `COMPLETE_INBOX_ITEM` (coordinator, coordinator_service), `DISPATCH_BROADCAST_ALERT` (coordinator, coordinator_service, bed_manager), `RAISE_REFERRAL` (coordinator, coordinator_service, ward, ed, community), `RECORD_BED_MEETING_ACTION` (coordinator, coordinator_service, officer, ward, bed_manager, ed, community, executive, admin), `RECORD_OBSERVATION_LEVEL` (coordinator, coordinator_service, officer, ward, bed_manager, ed, community, executive, admin), `RELEASE_INBOX_ITEM_OWNERSHIP` (coordinator, coordinator_service, officer, ward, bed_manager, ed, community, executive, admin), `REOPEN_INBOX_ITEM` (coordinator, coordinator_service), `SNOOZE_INBOX_ITEM` (coordinator, coordinator_service, officer, ward, bed_manager, ed, community, executive, admin), `TAKE_INBOX_ITEM_OWNERSHIP` (coordinator, coordinator_service, officer, ward, bed_manager, ed, community, executive, admin), `UNSNOOZE_INBOX_ITEM` (coordinator, coordinator_service, officer, ward, bed_manager, ed, community, executive, admin).
- **Screen gates written by hand.** Controls that check a role directly rather than through `useRoleGate` (for example `wardTasksAreActionableForRole`, `noticeIsMarkableByChrome`, `canBreakGlass` and screens rendered only on their own route) are not read here. `tests/ward-role-permissions.test.ts` pins the route-only screens to `EVENT_ROLE`.
- **A coordinator on another desk's route.** On a ward, ED, community or officer route a coordinator's screen acts as that route's role; the backend records the change as the coordinator's (`deskCommand`). The matrix asks the coordinator's own desk.
- **Place and record checks.** `commandScopeRefusal` and the reducer's own-unit narrowing need real records; the consolidated authority tests cover them.
- **Local demo without sign-in.** With no shared workspace every desk is a preview and the demo controls are on for all; this matrix is the signed-in workspace.
- **Demo controls** assume the server's `sharedDemoEvents` setting is on; with it off every desk is refused them.
