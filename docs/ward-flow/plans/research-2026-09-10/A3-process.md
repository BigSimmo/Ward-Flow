## 2. Fold protocol (from `HOW-TO-FOLD-2026-09-10.md`, which "supersedes any earlier description of folding," line 4)

1. Everyone except Ward Lead commits on their own branch and **hands Ward Lead a SHA**, never a branch name: _"Ward Lead is the only chat that folds. Everyone else commits on their own branch and hands Ward Lead SHAs."_ — `HOW-TO-FOLD-2026-09-10.md:6-7`.
2. The only destination is `codex/task-ward-flow-live-state-20260831`. `main` is never touched, "not even locally," not even a fast-forward — owner quote _"the ward flow line, not main"_ / _"never add to main... it must be Ward Flow!!!!"_ — `HOW-TO-FOLD-2026-09-10.md:11-18`; identical text in `worktree-ownership.md:1-8`.
3. Fold **by SHA**, never by branch name, because a branch name "resolves at read time" — `HOW-TO-FOLD-2026-09-10.md:29-32`. When checking a merge result, compare `MERGE_HEAD`, not the branch name: `cat "$(git rev-parse --git-dir)/MERGE_HEAD"` — `:34-39`.
4. To confirm landing, requester names an artefact check and the folder runs it — _"CONFIRM THE ARTEFACT, NOT THE FOLD… A fold confirmation is a claim about a SHA. The branch may have grown since."_ Example: `git show <ward-line>:docs/ward-flow/<file>.md | grep -c "<phrase>"` — `:43-56`.
5. Never use `git log -S` alone to ask "has this landed" — it "manufactures an absence" across a merge. Use `git merge-base --is-ancestor <sha> <ward-line>` — `:63-81`.
6. Point any checker at a known positive before trusting a negative: _"A checker that cannot say YES cannot be trusted when it says NO."_ Use `scripts/ward-flow/folded.sh`, which refuses to answer until it can prove a known-folded commit reads as folded — `:84-101`; three verdicts exist (folded / not folded / cannot tell) and collapsing "cannot tell" into "no" is the same error again.
7. Measure a contribution against the merge-base, not HEAD: `BASE=$(git merge-base HEAD <sha>); git diff --stat $BASE <sha>` — `git diff HEAD <sha>` alone reports every intervening commit as a deletion — `:104-112`.
8. Never fold a whole-tree format pass without running the full suite **after** the reformat and **before** folding it; never resolve a format conflict by picking a side — take the semantically newer content, then re-run prettier — `:116-134`.
9. Back up before every fold: `env -u MSYS2_ARG_CONV_EXCL bash ~/.claude/scripts/backup-work.sh`, then read the tip **out of** the bundle rather than trusting `git bundle verify` alone (it only checks a bundle against itself) — `:155-172`.
10. The fold commit itself must carry: the SHA/range folded (never the branch name); anything the contributor believed but had not measured, labelled as belief; anything withdrawn and why it looked persuasive; any conflict and which side was taken and why; what was **not** done — `:176-187`.

## 4. Chat-to-chat messaging (`how-chats-talk-to-each-other.md`, dated 2026-09-01)

- **Shape:** every claim names its tree and its measurer (rule 1, `:30-36`); mark which half of a reply is your own verification versus relayed — _"taking this from you, not verified"_ (rule 2, `:38-44`); cite by symbol name, a line number is only a hint (rule 5, `:64-69`); name the chat **and** the branch — _"the Builder"_ is ambiguous across three of them (`:157`).
- **Message immediately when:** you find something that makes another chat's work wrong (now, not buried in a report); you're about to need a path you don't own; a ruling you were given turns out false; you're handing back rather than reaching (`:144-149`).
- **Never message to:** ask if someone is finished (read `now.md` or git instead); relay an un-disambiguated ruling — _"a relay is a prompt to confirm, never a decision to act on"_ (`:151-155`); route a blocked/denied action through a sibling chat to get around a permission refusal (rule 6, `:71-78`).
- **Owner questions:** format is fixed in `how-to-write-to-the-owner.md` — detail first at whatever length is warranted, then a `Summary` block with labelled lines `DID / ISSUE / GAPS / NEED / RECOMMEND / NEXT`. `ISSUE` and `GAPS` always print, even as one word (`:32-34`). One recommendation, not a menu; if asked twice with no answer, stop asking and choose, noting the choice (`:53-54`). Route owner questions **through Ward Lead** where a role process exists — two chats independently asking the same question got two different honest answers (`handover-ward-builder-four-2026-09-10.md:87`; also the `main`-vs-ward-line incident, `worktree-ownership.md:14-17`).
