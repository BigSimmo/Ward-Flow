# Supabase setup

_Updated 2026-10-19 - migration runner, schema 11 and membership access checked against source; Documentation owns._

> [!IMPORTANT]
> **Repository & Data Boundary:** Project `zakzoemeedfepxcstsou` is a **dedicated, isolated Ward Flow synthetic-only Supabase project**. **PsychSift's Supabase project, database, and credentials must never be used in Ward Flow.** Ward Flow's optional shared workspace (the separate `backend/ward-flow/` server's `/v1/workspace*` routes) operates exclusively on **100% synthetic data** — zero real patient information (PII/PHI) is permitted.

Supabase is the current database and sign-in provider (decision D-55). [DATABASE.md](../../docs/ward-flow/DATABASE.md) is the single source of truth for the provider, the settings that select it and how to change it. Plain PostgreSQL (`postgres`) is the only other database adapter. The shared engine, `/v1/workspace` paths, snapshots, command receipts, immutable audit and revision conflicts are the same for both. All data remains synthetic.

Shared mode is opt-in through backend `WARD_SHARED_ENABLED=true` and browser `NEXT_PUBLIC_WARD_SHARED_ENABLED=true`. The synthetic offline demo remains available when browser shared mode is off. Push stays off by default.

## Approved Supabase target

Start with the [empty, non-secret settings template](infra/supabase-settings.template.env), keeping the completed private copy outside Git. Supply runtime connection details and the publishable key privately; no administrator connection belongs in that runtime file.

Only project `zakzoemeedfepxcstsou` is allowed. The direct target is `db.zakzoemeedfepxcstsou.supabase.co:5432/postgres` with login `wardflow_backend`; the session pooler is `aws-0-ap-southeast-2.pooler.supabase.com:5432/postgres` with login `wardflow_backend.zakzoemeedfepxcstsou`. The application refuses the administrator login and connection URL SSL overrides. These source restrictions do not prove a current hosted connection.

Before an authorised administrator operation, inspect the exact target, existing schema definitions, versions, ownership, effective grants, role flags/membership and nominated Auth account. Preserve a recoverable backup. Stop on incompatible existing objects; do not substitute a privileged runtime login.

Prefer `npm --prefix backend/ward-flow run migrate:supabase` (`migrate-supabase.mjs`) with a separate private `WARD_SUPABASE_MIGRATION_DATABASE_URL` administrator connection targeting the same host, port and database as `WARD_SUPABASE_DATABASE_URL`. The runner executes the read-only catalogue preflight (`verifyPostgresNamespace`), verifies migration file checksums, then applies pending migrations `001` through <!-- fact:latest-migration -->012-foreign-key-indexes<!-- /fact --> in one transaction under advisory lock `782322`. It installs [runtime grants](infra/supabase-runtime-role.sql) in a separate transaction, including revoking `PUBLIC` `CREATE` on `schema public` and setting `statement_timeout`, `idle_in_transaction_session_timeout`, and `lock_timeout` on `wardflow_backend`. A manual alternative must preserve that preflight, checksum and version validation, ordered migration transaction, stop-on-error rollback and concurrency lock, followed by the grants transaction; executing individual SQL files without these safeguards is insufficient.

Runtime startup never migrates. Shared readiness requires migrations 1 through 5 and accepts later versions through <!-- fact:latest-migration -->012-foreign-key-indexes<!-- /fact -->. Migration 6 adds row-level security; 7 permits prototype workspaces only; 8 adds memberships and break glass; 9 adds cover, access requests, last-used times and phone alerts by role; 10 moves workspace records to individual rows atomically; 11 adds append-only record access history, protects break glass rows against changes and records server-side session sign-outs. Before 11, record opens are not logged and sign-out does not revoke the session here. 12 adds an index for each of the 13 foreign keys that had none; it changes no table, row, grant or policy.

For separately authorised rollback, run the matching script in one stop-on-error transaction, starting with [12](infra/rollback-012-foreign-key-indexes.sql), then [11](infra/rollback-011-record-access-and-sign-out.sql), [10](infra/rollback-010-workspace-records.sql), [9](infra/rollback-009-access-cover-requests.sql), [8](infra/rollback-008-role-access.sql), [7](infra/rollback-007-prototype-only.sql) and [6](infra/rollback-006-row-level-security.sql). Rollback 11 drops the record access and sign-out tables and removes break glass edit protection; preserve required access history first. Rollback 8 refuses once audit rows name a role or place other than the statewide coordinator, so after roles have been used the chain stops at 8. Reapply runtime grants after each forward migration from 8 through 12. Deploy a backend that accepts the target schema before migrating: an older backend refuses a version it does not know.

Repeat explicit schema/table/sequence/function revocations after future migrations. Per-schema function defaults cannot cancel PostgreSQL's global PUBLIC EXECUTE default; browser schema USAGE remains denied. The separate [Supabase helper hardening script](infra/supabase-security-hardening.sql) is optional provider-specific administrator work and refuses an unexpected helper identity. Do not apply it to plain PostgreSQL.

Set the runtime password privately, separate from Git. Use a private backend environment with `WARD_DATABASE_PROVIDER=supabase`, `WARD_AUTH_PROVIDER=supabase`, the shared/prototype selectors, approved project reference/URL, `WARD_SUPABASE_DATABASE_URL`, `WARD_SUPABASE_PUBLISHABLE_KEY`, verified `WARD_COORDINATOR_USER_IDS`, a synthetic `WARD_WORKSPACE_ID`, verified `WARD_ALLOWED_ORIGIN` and `WARD_TRUSTED_PROXY_ADDRESSES`. Prefer an explicit proxy socket allowlist. `*` requires verified proxy-only ingress that overwrites forwarded client headers and prevents direct access; leave empty when unverified. Set `WARD_SUPABASE_CA_CERT_FILE` when the project's CA is not already trusted by Node. CA bundles and private files stay outside deployment archives. TLS certificate and hostname verification remain enabled.

The backend uses only a publishable key to verify the sign-in token through the approved Auth service. Service-role and secret keys are refused. The verified account UUID identifies the user; the server resolves its working role from the coordinator bootstrap allowlist or, from migration 8, an active `ward_flow.memberships` row. Browser email, role and signup fields cannot grant access. Verification has a deadline covering both response headers and body reads. Invalid credentials are denied; provider outages return a retryable verification error.

Build the engine and start the backend with the private runtime environment. For the browser set `NEXT_PUBLIC_WARD_AUTH_PROVIDER=supabase` (now the default when omitted), the actual backend origin in `NEXT_PUBLIC_WARD_API_BASE_URL`, the approved Supabase URL and its publishable key. Never expose administrator/service-role credentials. The optional nominated signup email is a UI restriction, not the Auth service's registration policy. Keep the provider's confirmation/recovery and registration settings under their separate administrator authority.

Run `npm run ensure`, verify `/api/local-project-id` and use that actual frontend origin in the backend and provider allowlists. After separately authorised provider setup, verify authenticated readiness, sign-in, shared save/reload, restart persistence, stale revisions and retries. Offline proof does not establish these live results. No live migration, provider mutation, new paid service or deployment is performed by this source rebuild.

## Switching and recovery

Finish or abandon pending work, sign out and stop owned processes before switching presets. A previously accepted transaction can still commit. Preserve private configurations separately, select matching database/auth/browser settings, rebuild public browser configuration and restart. Switching selectors transfers no records. To change provider, follow [DATABASE.md](../../docs/ward-flow/DATABASE.md). Generic PostgreSQL setup (`WARD_DATABASE_PROVIDER=postgres`) has its own [administrator and recovery flow](SETUP-POSTGRES.md).

Keep preserved recovery archives and their separate owner-held keys outside the checkout. This guide makes no claim about their current contents, a cloud-data export or a deployed revision. Restoration, data transfer, deployment and provider acceptance each require separate authority and evidence.

To prune expired command idempotency receipts (`ward_flow.commands` rows older than seven days by the database clock; the CLI uses the fixed `RECEIPT_RETENTION_DAYS` constant in `prune-receipts.mjs` and reads no retention override from the environment) while keeping the append-only `ward_flow.audit` history intact, run `node --env-file=<absolute-path-to-private-migration.env> backend/ward-flow/prune-receipts.mjs supabase` (for example `C:/private/ward-migration.env` on Windows) with `WARD_SUPABASE_MIGRATION_DATABASE_URL` and `WARD_SUPABASE_DATABASE_URL` configured in that private migration environment (or use the npm aliases after exporting the required variables). Because `wardflow_backend` has no `DELETE` grant on `ward_flow.commands`, receipt pruning runs with the migration identity after `verifyPostgresNamespace`.
